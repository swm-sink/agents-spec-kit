# Design Eval Spec

## When to use

Use this skill when the user wants to **design (not run) an evaluation for an AI agent**. Concrete trigger phrases: "design an eval", "how do I test my agent", "set up Inspect AI tasks", "what scenarios should I evaluate", "write an eval spec".

Skip this skill when:
- The user wants to *run* an existing eval. They need a runtime (Inspect AI, promptfoo), not this skill.
- The user wants generic LLM benchmarking (HellaSwag, MMLU). This skill is about agent-level evals — multi-turn, tool-using, task-grounded.

## How to use

1. **Gather inputs.** You need:
   - The agent's spec (or a description of what it does + capabilities).
   - The agent's failure modes (what it must NOT do).
   - The user's evaluation budget — one-shot review, CI loop, weekly batch?
   - Whether they have real data or need synthetic.

2. **Sketch scenarios.** Aim for 5–10 in v1. Each scenario maps to one observable behavior. Mix:
   - **Happy path** — typical user request, standard expected output. (~40% of scenarios)
   - **Edge case** — unusual input, sparse context, multi-turn ambiguity. (~30%)
   - **Anti-pattern** — failure mode the agent must NOT exhibit (proposing a destructive action without confirmation, hallucinating a file path, leaking PII). (~30%)

   For each scenario, write:
   - **Setup**: initial state (files, env, prior turns).
   - **Input**: what's given to the agent.
   - **Expected behavior**: what success looks like, observable from outside.
   - **Pass criterion**: the rule that decides pass/fail.

3. **Pick a scorer per scenario.** Reach for the simplest:
   - **Exact match** — output equals a reference string. (Best for classification, known commands.)
   - **Structural / regex** — output contains/matches a pattern. (Best for "must include file X", "must NOT propose `rm -rf`".)
   - **Model-graded** — a separate LLM call grades the output against a rubric. (Use when output is open-ended; specify the rubric explicitly.)
   - **Human review** — manual yes/no. (Use when other scorers are gameable; budget accordingly.)

4. **Decide the dataset.** Three sources:
   - **Hand-written** — fastest to start; ~10–20 items. Best for v1.
   - **Sampled from production** — real user inputs (with consent / scrub PII). Better signal, more setup.
   - **Synthetic** — generated by another LLM. Cheap at scale but biased toward what the generator finds easy.

   Recommend hand-written for v1 unless the user has production data ready.

5. **Set pass thresholds:**
   - Per-scenario: `K of N trials must pass` (e.g., 9/10 — handles model nondeterminism).
   - Aggregate: `≥X% of scenarios pass`.
   - Anti-pattern scenarios should be 100% — the agent must NEVER exhibit the failure.

6. **Pick a runtime.** Recommend:
   - **Inspect AI** — for serious eval work. Python. Adopted by Anthropic/DeepMind/xAI. Maps cleanly to our scenarios.
   - **promptfoo** — YAML-first, lighter weight, good for prompt-comparison evals.
   - **Hand-rolled Python script** — for one-shot reviews of < 10 scenarios.
   The eval-spec is plain Markdown either way; the runtime decision affects how it's wired up.

7. **Write the spec** following the structure documented in `templates/commands/agent.eval.md` (the slash command also describes the same shape). At minimum:
   - What we're evaluating
   - Scenarios (with setup/input/expected/scorer/threshold)
   - Dataset (source, size, format)
   - Scorers (definitions)
   - Run plan (runtime, frequency, pass bar, cost)
   - Out of scope
   - Risks

8. **Sanity-check before handing back:**
   - Does each success criterion in the agent spec map to ≥1 scenario?
   - Is at least one scenario testing a failure mode?
   - Are the pass thresholds concrete (not "looks reasonable")?

## Examples

### Example 1 — code-review subagent
**User says:** "Design an eval for my code-reviewer subagent."
**You produce:** 8 scenarios — 3 happy path (find a real bug in a small diff, recommend a refactor, approve a clean change), 2 edge (empty diff, generated code), 3 anti-pattern (don't approve obviously broken code, don't fabricate file paths, don't propose destructive `git reset`). Scorers: structural for the anti-patterns ("output must NOT contain `rm -rf` or `git reset --hard`"), model-graded with a rubric for the happy paths. Dataset: 10 hand-written diffs. Runtime: Inspect AI. Pass bar: 100% on anti-patterns, ≥80% on the rest.

### Example 2 — issue triager skill
**User says:** "I want to evaluate that my triage skill labels issues correctly."
**You produce:** 15 scenarios — real issue text → expected label set. Scorer: exact match on the label list (set comparison). Dataset: 20 hand-labeled issues. Runtime: hand-rolled script (it's literally a classification task). Pass bar: ≥85% set-equality.

## Anti-patterns

- **Don't write 50 scenarios for v1.** Five well-chosen scenarios > 50 noisy ones. Add more after the v1 eval is running.
- **Don't pick model-graded for everything.** It's expensive, slow, and adds variance. Use exact / structural where you can.
- **Don't skip anti-pattern scenarios.** "We didn't think about failure modes" is the single most common eval gap.
- **Don't write evals for things the agent doesn't actually do.** Stick to capabilities listed in the agent spec; aspirational evals just produce noise.
